Using them

One ticket, end to end. Each command takes the ticket id, and each phase refuses to start if the constitution is not readable in the session — so install architecture-core alongside ticket-delivery. 

/ticket-analysis ABC-123
/implementation-phase ABC-123
/test-on-localhost ABC-123
/pr-review ABC-123

Against a deployed environment the base URL is passed in, never guessed from a naming convention: 

/cloud-test https://my-service.fly.dev ABC-123

Any standard can also be reached directly, without a ticket — /fly-io-deployment before writing a fly.toml, /security-review before something goes public. If a bare name collides with another plugin's, the namespaced form always works: /ticket-delivery:implementation-phase.

What this is

Most architecture documents are written once, from first principles, and then quietly diverge from the systems they claim to govern. This one runs the other way: every rule here generalises something a repository in the estate already does — or demonstrably failed to do — and each guide cites the worked example it came from.

It ships three ways. As documentation you read. As installable skills an agent loads when a standard applies, so it has the rule instead of re-deriving it from whatever code it happens to see. And as procedures you invoke by name — /ticket-analysis, /implementation-phase, /pr-review — which run one ticket through those same standards, cite the principle behind every rule they apply, and stop rather than guess if the constitution is not readable in the session. The packaging follows Agent Plugins 1.0.0, the vendor-neutral format behind GitHub Copilot, VS Code, Claude Code, Cursor and Codex, so one tree serves every client.

Install

Start with architecture-core — it carries the constitution, the session playbook and the repository baseline, and the other plugins assume it. Every client reads the repository's default branch.

ticket-delivery is the one that changes how a session is driven rather than what it knows. Its phases refuse to run without the constitution in front of them, so install it alongside architecture-core rather than on its own — WORKFLOW.md is the flow, the commands and when to break the sequence.

Claude Code

/plugin marketplace add konradcinkusz/architecture-standards
/plugin install architecture-core@architecture-standards

GitHub Copilot CLI

copilot plugin marketplace add konradcinkusz/architecture-standards
copilot plugin install architecture-core@architecture-standards

VS Code — settings.json

{
  "chat.plugins.marketplaces": [
    "konradcinkusz/architecture-standards"
  ]
}

A whole team, without anyone running a command

{
  "extraKnownMarketplaces": {
    "architecture-standards": {
      "source": { "source": "github", "repo": "konradcinkusz/architecture-standards" }
    }
  },
  "enabledPlugins": {
    "architecture-core@architecture-standards": true
  }
}

Commit that to a consuming repository's .claude/settings.json and every clone gets the standards. Any other agent can skip the install entirely: attach this repo as a sibling checkout and point it at AGENTS.md.

The six plugins

Most skills are short routers — when it applies, its failure modes, its checklist — with the full standard bundled underneath it in references/. Agents load the reference only when the skill actually fires, so twenty-six standards cost nothing until one is needed. ticket-delivery is the exception: its skills are procedures you invoke, so each carries its document as its body.

architecture-core

4 skills · 3 agents · install first

The constitution (P1–P15), the review / modernize / recover session playbook, the master delivery prompt, and the repository baseline.

deployment-and-platform

7 skills

Fly.io, Azure AI Foundry agents, Azure operations, per-PR preview environments, and customer-hosted private-cloud delivery.

services-and-clients

6 skills

HTTP and API plumbing, identity and accounts, payments and metering, Next.js frontends and BFFs, and browser extensions.

quality-and-process

8 skills

LLM evaluation, testing strategy, E2E acceptance suites, security review, open-source release, and README badges.

research-standards

1 skill · bundled templates

How a repository documents scientific research: the layout, the study shape, the evidence rules, plus the study and LaTeX paper templates.

ticket-delivery

5 skills · procedures, not routers

The per-ticket procedure you invoke rather than paste: ticket analysis and the gate into implementation, the implementation phase itself, two optional API verification passes — local and deployed — and the review of a pull request against its ticket.

On the worked examples

The rules here are repo-agnostic; the evidence behind them is cited at the end of each guide. Public sources — copilot-scope and authservice — are named and linkable.

Private ones appear under stable placeholders (<saas>, <consumer>, <legacy-monorepo> and friends), so a citation still shows you the shape a rule came from without publishing the repository behind it.
